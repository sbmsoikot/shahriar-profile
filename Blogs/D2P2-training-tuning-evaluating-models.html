02 / FOUNDATIONSDeep learning fundamentals: from neuron to CNN to RNN

A neural network is a directed graph of neurons organised into layers. Each neuron computes a weighted sum of its inputs, applies an activation function, and passes the result forward. The network learns by comparing its output against the true label (the loss), then propagating the error backwards through every layer to adjust the weights — backpropagation. Deep simply means many layers, which lets the network learn hierarchical representations: edges → shapes → objects → concepts.

Convolutional Neural Networks (CNNs)

CNNs are built for spatial data — images, primarily. Instead of connecting every neuron to every pixel, a CNN slides small filters (kernels) across the image to detect local features (edges, curves, textures). Each filter produces a feature map; pooling layers reduce the spatial size while retaining the most important activations; deeper layers compose simple features into complex ones. The result is a model that's translation-invariant — it recognises a crack in a MetroPulse scooter wherever it appears in the frame. SageMaker's Image Classification and Object Detection built-ins are both CNN-based under the hood.

Recurrent Neural Networks (RNNs) & the vanishing gradient

RNNs process sequences by maintaining a hidden state that carries context from one time step to the next — natural for demand forecasting, where today's ride count depends on yesterday's. The problem: in plain RNNs, that carried state gets multiplied through many time steps during backpropagation; gradients vanish or explode. Long Short-Term Memory (LSTM) networks solve this with gating mechanisms (forget gate, input gate, output gate) that selectively remember and discard information over long sequences. GRUs (Gated Recurrent Units) are a lighter alternative with fewer parameters and similar effectiveness.

The vanishing gradient problem isn't unique to RNNs: it affects any deep network where small gradients get multiplied through many layers until they round to zero, leaving early layers essentially untrained. The toolkit of fixes: ReLU activation (no saturation for positive inputs), batch normalisation (re-centres layer activations to prevent scale explosion), residual (skip) connections (shortcut gradients past blocks of layers), and gradient clipping (caps the magnitude so they don't explode either).

Exam lens "Training loss stops improving in early layers" or "very deep network with poor convergence" → vanishing gradient. Remedies to know: switch to ReLU; add batch norm; use residual connections; try gradient clipping. LSTM vs RNN → LSTM for long sequences; LSTMs have gating mechanisms RNNs lack.

03 / DISCIPLINETuning, regularization & ensemble methods

A model that memorises the training set is useless on real MetroPulse data. Regularization is the discipline of keeping models honest — making them generalise rather than overfit. The three "knobs" you touch most, in order of impact:

Learning rate controls how large a step gradient descent takes each iteration. Too large and the loss oscillates or diverges; too small and training stalls. In practice, a learning rate schedule starts higher, then decays — or uses adaptive optimisers (Adam, AdaGrad) that tune it per parameter. Batch size controls how many examples you average a gradient over: smaller batches are noisier (which can aid generalisation), larger batches are more stable but want a higher learning rate. Epochs is simply how many full passes over the training data; more isn't better once the model has peaked on validation data.

Dropout gotcha Dropout is only active during training. At inference time all neurons are live. If a question says "predictions are high-variance at deployment" and Dropout is enabled in inference mode, that's the bug — not a feature.

Ensemble methods: Bagging vs Boosting

Individual models are fragile. Ensembles aggregate many to reduce that fragility. Bagging (bootstrap aggregating) trains multiple independent models on random subsets of the data (sampled with replacement) and averages their predictions — reducing variance. Random Forest is the canonical implementation (bagging + random feature subsets per tree). Boosting trains models sequentially: each one focuses on the examples the previous got wrong. The sequence compounds into a strong predictor by correcting bias. XGBoost, LightGBM, and GBM are all gradient-boosted tree ensembles — this is exactly what we're using for MetroPulse predictive maintenance.

Exam lens Bagging = parallel, reduces variance, models are independent (→ Random Forest). Boosting = sequential, reduces bias, each model corrects the last (→ XGBoost). If a question asks about a model that is prone to overfitting on noisy data, boosting is the riskier one; bagging is more robust to noise.

04 / MEASUREEvaluation: the metrics that actually matter

Every model needs a verdict. Picking the wrong metric is as bad as picking the wrong algorithm — a fraud model measured by accuracy is a disaster, because "predict no fraud ever" scores 99.7%. Here's the toolkit, matched to MetroPulse's specific problems.

Regression metrics: forecasting demand accurately

When the output is a continuous number — how many rides per station per hour — the right metrics are: RMSE (root mean squared error) squares each error before averaging, so large misses are penalised heavily; useful when big errors are especially costly. MAE (mean absolute error) takes the raw average of absolute errors — more robust to outliers and directly interpretable (e.g., "±18 rides per hour on average"). R² (coefficient of determination) measures what proportion of the target's variance the model explains: 1.0 is perfect; 0 means the model is no better than always predicting the mean; negative means it's actively worse.

MetroPulse problemMetric of recordWhy
Damage-photo classifierF1 / AUC-ROCImbalanced — most photos are fine
Fraud detectionRecall (+ AUC)Missing fraud costs more than false alarms
Predictive maintenancePrecision + RecallBalance: over-maintenance vs downtime
Demand forecastingRMSE (peak hours) + MAEBig misses are expensive; MAE for interpretability
Exam lens "Imbalanced classes" → F1 or AUC-ROC, not accuracy. "Outliers in regression" → MAE over RMSE. "Diagnose a classifier's specific errors" → confusion matrix. "Threshold-independent ranking" → AUC. And precision vs recall: minimise false alarms → precision; minimise misses → recall.

05 / LAUNCHLaunching training jobs in SageMaker AI

SageMaker AI abstracts infrastructure so the only decisions are the interesting ones. The universal entry point is the Estimator — an object that specifies what code to run, on what instance, with what data channels, and with what hyperparameters. Underneath, SageMaker provisions the instances, loads the right training container (a Docker image with the framework pre-installed and AWS-optimised), copies data from S3, runs the script, and saves model artifacts back to S3.

AWS ships pre-built Deep Learning Containers (DLCs) for TensorFlow, PyTorch, MXNet, and more — each one tuned for GPU efficiency, pre-loaded with CUDA and cuDNN, and maintained by AWS. You use a DLC when you have a custom training script; you use a built-in algorithm's own container when you want the algorithm with minimal code.

// Train MetroPulse predictive-maintenance XGBoost via the SageMaker SDK

import sagemaker
from sagemaker import image_uris, TrainingJobAnalytics
from sagemaker.estimator import Estimator

session = sagemaker.Session()
role    = sagemaker.get_execution_role()

# built-in XGBoost container image for this region
container = image_uris.retrieve("xgboost", session.boto_region_name, version="1.7-1")

xgb = Estimator(
    image_uri        = container,
    role             = role,
    instance_type    = "ml.m5.xlarge",
    instance_count   = 1,
    output_path      = "s3://metropulse-lake/models/maintenance/",
    hyperparameters  = {
        "max_depth": 5, "eta": 0.2, "num_round": 100,
        "objective": "binary:logistic", "eval_metric": "auc"
    },
)
xgb.fit({"train": train_s3, "validation": val_s3})  # channels map to S3 paths

The same Estimator pattern connects to every SageMaker tool in this post — Automatic Model Tuning, Debugger, and Experiments all wrap or extend it without requiring a different code style.

06 / TUNEAutomatic Model Tuning (AMT) & hyperparameter optimisation

Hyperparameters — learning rate, max depth, dropout rate — are not learned by the model; they're set by the engineer. Manually guessing and relaunching jobs is expensive and slow. SageMaker Automatic Model Tuning (AMT) launches parallel training jobs across a defined hyperparameter search space, tracks which combinations produce the best validation metric, and surfaces the winner. It's the difference between systematic optimisation and guesswork.

SageMaker AMT also supports Hyperband, a bandit-based approach that starts many jobs at low resource (few epochs) and kills underperformers early, giving survivors more compute. For most MetroPulse tuning jobs, Bayesian is the default recommendation — it uses fewer trials to find a good set of hyperparameters.

// Wrap the XGBoost Estimator in a HyperparameterTuner

from sagemaker.tuner import HyperparameterTuner, ContinuousParameter, IntegerParameter

tuner = HyperparameterTuner(
    estimator         = xgb,              # the Estimator from section 05
    objective_metric_name = "validation:auc",
    objective_type    = "Maximize",
    hyperparameter_ranges = {
        "eta"       : ContinuousParameter(0.01, 0.5),
        "max_depth" : IntegerParameter(3, 9),
        "num_round" : IntegerParameter(50, 300),
    },
    strategy          = "Bayesian",
    max_jobs          = 20,
    max_parallel_jobs = 4,
)
tuner.fit({"train": train_s3, "validation": val_s3})

07 / AUTOMLSageMaker Autopilot: AutoML end to end

AMT requires you to know which algorithm you're tuning. SageMaker Autopilot removes even that step: point it at a labelled tabular dataset, tell it the target column, and it runs the entire ML pipeline automatically — data preprocessing, algorithm selection (from linear models to XGBoost to neural networks), hyperparameter tuning, and a ranked leaderboard of candidate models you can inspect and deploy.

Location change Autopilot's UI moved into SageMaker Canvas (since November 2023); you access it through the Canvas application in SageMaker Unified Studio, not in the old Studio Classic. The API and SDK (for scripted AutoML jobs) remain unchanged. If a question says "Autopilot is unavailable" after the migration, the answer is: open Canvas.

Autopilot outputs a model leaderboard — ranked candidate models with their validation metrics and explainability reports — so you maintain full visibility even though you didn't specify the algorithm. The best candidate can be deployed with one click or promoted to a SageMaker Pipeline step for production.

08 / OBSERVEExperiments, Debugger, Model Registry & TensorBoard

Training a model is not a single run — it's dozens of experiments, each with different hyperparameters, datasets, or architectures. SageMaker AI's observability and governance stack keeps all of that organised.

SageMaker Experiments automatically logs every training run (or you can log explicitly) with its hyperparameters, metrics, and artifacts. Runs are grouped into experiments so you can compare 20 tuning runs side-by-side, filter for the top-3 by AUC, and reproduce any run exactly from its logged configuration. For MetroPulse, each model problem (maintenance, demand, damage) gets its own experiment; every trial in the AMT tuning job becomes an automatically-tracked run.

SageMaker Debugger is more surgical — it hooks into a running training job (with zero or minimal code changes) and emits tensors at defined intervals. Built-in rules flag known pathologies in real time: a vanishing gradient (section 02's enemy), an exploding gradient, an overfit (training AUC keeps rising; validation flat), or dead neurons (neurons that never activate). Debugger can stop the job automatically when a rule fires — saving GPU-hours. It also integrates directly with TensorBoard: Debugger writes tensors to S3, and you visualise training curves, weight histograms, and profiling timelines in TensorBoard in SageMaker Studio.

SageMaker Model Registry is the governance layer for trained artifacts. A model is registered with its metadata (training job, metrics, data lineage), assigned a version, and given an approval status (PendingManualApproval → Approved → Rejected). Only Approved models flow into production. This makes the release process auditable — a requirement in any regulated environment (mobility companies are subject to safety standards). Models in the registry can be deployed directly or consumed by SageMaker Pipelines (covered in the MLOps post).

Exam lens Map each tool to its job: Experiments = track and compare runs; Debugger = diagnose issues in a live training job (vanishing grad, overfit, dead neurons); TensorBoard = visualise training curves and tensors; Model Registry = version + approve models for production. "How do you stop a training job when overfitting is detected?" → Debugger with an overfitting rule.

09 / SCALE-UPTraining at scale: Compiler, Warm Pools & checkpointing

Once a model is worth training seriously, the focus shifts to doing it faster and more cheaply without changing the result.

SageMaker Training Compiler accelerates deep learning training by automatically compiling model graphs to optimised GPU code — kernel fusion, operator merging, and mixed-precision arithmetic (FP16/BF16 alongside FP32 where precision matters). For the MetroPulse damage-photo CNN, Training Compiler can reduce training time by 10–50% with a single flag, at no change to model quality or accuracy.

SageMaker Managed Warm Pools keep the training infrastructure warm between jobs. Normally, each training job spins up a fresh instance (a process that takes 2–5 minutes); Warm Pools retain the provisioned cluster for a configurable window so the next job in a tuning run starts in seconds. For a 20-job AMT run, that saving compounds significantly.

Checkpointing saves the model's state (weights, optimiser state, training step) to S3 at regular intervals. If a spot instance is reclaimed or a node fails mid-job, training resumes from the last checkpoint rather than restarting from scratch — essential for long-running deep learning jobs. SageMaker pairs checkpointing with Automatic Restarts and Cluster Health Checks: unhealthy nodes are automatically replaced, and training continues from the checkpoint. For MetroPulse's demand-forecasting LSTM (which might train for hours on months of ride history), this turns infrastructure failures from disasters into minor interruptions.

Exam lens "Reduce training time without changing the model" → Training Compiler. "Eliminate startup overhead between sequential tuning runs" → Warm Pools. "Resume training after a spot interruption" → Checkpointing. These three are distinct answers to three distinct operational constraints.

10 / SCALE-OUTDistributed training: data parallelism, model parallelism & MiCS

When a single GPU isn't enough — because the dataset is too large, the model doesn't fit in memory, or you simply want to train faster — you distribute. There are two fundamentally different reasons to go distributed, and they call for different strategies.

Data parallelism (SMDDP) is the right choice when training throughput is the bottleneck and the model fits comfortably on one GPU — DeepAR on MetroPulse's ride history, for instance. SMDDP replaces NCCL's ring-based AllReduce with a topology-aware algorithm optimised for AWS infrastructure, achieving up to 40% better performance on large clusters. The hardware enabler underneath is Elastic Fabric Adapter (EFA): a specialised network interface that bypasses the OS kernel for low-latency, high-throughput inter-node communication. Without EFA, distributed training on GPU clusters is bottlenecked by standard networking overhead.

Model parallelism (SMP) is the right choice when the model itself is too large to fit in a single GPU's memory — think very large language models. The model is partitioned across GPUs (pipeline parallelism splits by layer; tensor parallelism splits individual large operations). MiCS (Minimizes Communication Scale, also known as sharded data parallelism) is the AWS-developed hybrid: instead of sharding model state across the entire cluster (which incurs expensive global collectives), MiCS groups GPUs into partition groups where each group holds one full replica. Synchronisation happens within groups, not cluster-wide — near-linear scaling with dramatically less communication overhead.

Exam lens EFA = the network hardware that enables fast distributed training. SMDDP = data parallelism library (splits batches, optimised AllReduce). SMP = model parallelism (splits the model). MiCS = sharded data parallelism (partitions model state across partition groups, minimises communication scale). "Model doesn't fit on one GPU" → SMP. "Faster multi-GPU training for a model that fits" → SMDDP. "Huge model, huge cluster, communication cost is the bottleneck" → MiCS.

12 / RECALLDomain 2, Part 2 cheat-sheet

Training, tuning & evaluation

  • Activation functions: ReLU (default hidden layers), Leaky ReLU (dying ReLU fix), Sigmoid/tanh (saturate → vanishing grad), Softmax (multi-class output).
  • CNNs for spatial/image data (sliding filters → feature maps → pooling). RNNs for sequences; LSTMs use gates to preserve long-range context.
  • Vanishing gradient: gradients shrink through deep layers → fixes: ReLU, batch norm, residual connections, gradient clipping.
  • Regularisation: Dropout (training only), Early Stopping (save best checkpoint), L1 (sparsity/feature selection), L2 (weight decay/ridge).
  • Ensembles: Bagging = parallel, reduces variance (→ Random Forest); Boosting = sequential, reduces bias (→ XGBoost, LightGBM).
  • Classification metrics: Precision = no false alarms; Recall = no misses; F1 = balance both; AUC-ROC = threshold-independent discrimination. Imbalanced → F1/AUC, never raw accuracy.
  • Regression metrics: RMSE (penalises large errors); MAE (outlier-robust, interpretable); R² (variance explained; 0 = no better than mean).
  • SageMaker AMT: Bayesian HPO (sample-efficient, recommended), Random (parallelisable), Grid (small discrete only), Hyperband (pruning for deep learning).
  • Autopilot: AutoML — no algorithm knowledge needed; UI now in SageMaker Canvas; API unchanged. Use when algorithm choice is unknown or for fast baseline.
  • Experiments = track/compare runs; Debugger = detect live training issues (vanishing grad, overfitting, dead neurons); Model Registry = version + approval gate; TensorBoard = visualise curves and tensors.
  • Scale-up: Training Compiler (faster kernels); Warm Pools (no cold-start); Checkpointing + Automatic Restarts (resilience).
  • Distributed: SMDDP = data parallelism (batch split, optimised AllReduce via EFA); SMP = model parallelism (model split, pipeline + tensor); MiCS = sharded data parallelism (partition groups minimise communication scale). EFA is the low-latency network fabric enabling all three.
