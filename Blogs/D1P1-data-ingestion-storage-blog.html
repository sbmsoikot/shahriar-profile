Where Machine Learning Really Begins: Data Ingestion & Storage on AWS

No model survives bad plumbing. Before a single feature is engineered, the data has to be captured, moved, and stored correctly. Here's how I'd architect that layer — explained through one realistic build.

Domain 1, “Data Preparation for Machine Learning,” is the single heaviest-weighted area of the MLA-C01 exam at 28% of scored content. It's also where most production ML projects quietly succeed or fail.

This is the first post in a six-part series I'm writing as I work through the AWS Certified Machine Learning Engineer – Associate certification. Domain 1 is large enough that I'm splitting it across two posts: this one covers ingestion and storage; Part 2 will cover data transformation, integrity, and feature engineering. Rather than march through a feature checklist, I want to do what an architect actually does: pick a believable problem and let the services earn their place in the design. By the end, every concept from the “Data Ingestion and Storage” module — types of data, the three V's, lakes and lakehouses, data mesh, S3 and its many features, block and file storage, Kinesis, Apache Flink, and Amazon MSK — will have shown up because the build needed it, not because a syllabus listed it.

Let me introduce the company we're building for.

01 / THE SCENARIOMetroPulse: a city-scale mobility platform

The brief

MetroPulse Mobility

MetroPulse operates a fleet of e-scooters, e-bikes, and shuttle vans across a mid-sized city. Tens of thousands of vehicles emit telemetry every few seconds; riders book and pay through a mobile app; partner transit agencies share schedule feeds. The data team needs to:

  • Detect anomalies in real time — a battery draining abnormally fast, or a ride pattern that looks like payment fraud.
  • Land every event in a durable, queryable data lake to train demand-forecasting and predictive-maintenance models.
  • Give data scientists fast, shared access to training datasets without copying terabytes around.
  • Keep all of it secure, compliant, and cost-controlled as data ages from hot to cold.

That brief maps cleanly onto the three jobs of this layer: ingest (get data in, in batch and in real time), store (durably, at the right cost, with the right access), and organize (so the rest of the ML lifecycle can use it). Here's the shape of what we're building before we zoom into the pieces.

02 / FOUNDATIONSKnow your data before you store it

Every storage and ingestion decision downstream is dictated by the shape of the incoming data. MetroPulse produces all three classic categories at once, which is exactly why it's a good teaching example:

Structured data — fixed schema, rows and columns. MetroPulse's ride records (rider ID, start time, distance, fare) live here. It fits naturally in relational databases and columnar formats.

Semi-structured data — has tags or keys but no rigid table schema. The vehicle telemetry arrives as JSON: { "vehicle_id": "...", "battery": 0.62, "lat": ..., "lng": ... }. The schema can evolve (a new firmware adds a field) without breaking everything.

Unstructured data — no predefined model: the maintenance photos riders upload, support-call audio, free-text trouble tickets. This is where object storage (S3) becomes non-negotiable, and where ML feature extraction does the heavy lifting.

The “V's” that decide your architecture

AWS material frames data engineering challenges around the properties of big data — the “three V's,” often extended to five. They aren't trivia; each V points at a specific design lever.

Exam lens The MLA-C01 won't ask you to recite definitions. It will give a scenario — “high-velocity sensor data needs sub-second analysis” — and expect you to reach for the streaming stack, not a nightly batch job. Read for the V that's stressed and match it to the service.

03 / SOURCES & FORMATSCommon data sources and the formats that matter

Data reaches an ML platform from predictable places: operational databases (RDS/Aurora, DynamoDB), applications emitting events, logs and clickstreams, IoT devices and sensors, public/third-party datasets, and files dropped into object storage. MetroPulse touches almost all of them.

Format choice is one of the most under-appreciated cost-and-performance levers in the whole pipeline. The short version:

FormatShapeBest forMetroPulse use
CSVRow, textHuman-readable interchange, small extractsPartner CSV drops
JSONRow, semi-structuredFlexible/evolving event payloadsRaw telemetry & app events
AvroRow, binary + schemaStreaming, schema evolutionKafka/MSK topics
ParquetColumnar, binaryAnalytics & ML reads, compressionSilver/Gold lake zones
ORCColumnar, binaryHive/Big-data analyticsAlternative to Parquet

The pattern to internalize: row formats for writing/streaming, columnar formats for reading/analytics. Telemetry lands as JSON because producers are simple and the schema flexes. But before our models read it back hundreds of times, ETL rewrites it to Parquet — columnar storage means a query for “average battery drain by model” scans only two columns instead of every byte, slashing both scan time and cost in Athena.

04 / STORAGE PARADIGMSWarehouse, lake, or lakehouse?

MetroPulse needs to serve two very different consumers: BI analysts who want clean, governed tables, and data scientists who want raw, high-volume, multi-format data for feature engineering. That tension is exactly what the warehouse/lake/lakehouse debate is about.

For MetroPulse, a pure warehouse would choke on the raw telemetry volume and can't store rider photos at all. A pure lake risks becoming a “data swamp.” So we build a lakehouse: S3 as the storage substrate, open table formats (Apache Iceberg) for ACID transactions and schema evolution, and AWS Lake Formation for centralized, fine-grained governance. Analysts query the governed Gold tables; scientists reach into Silver and Bronze. One copy of data, two audiences.

05 / ORGANIZATIONData mesh: who owns what

A lakehouse solves where data lives. A data mesh answers who is responsible for it. Instead of one central team being a bottleneck for every dataset, a mesh treats data as a product owned by the domain that knows it best. At MetroPulse that means three domains — Rides, Fleet, and Payments — each publishing well-documented, discoverable, trustworthy data products into a shared platform. On AWS, this is typically implemented with separate accounts, Lake Formation permissions, and AWS Glue Data Catalog sharing.

Concept check Lakehouse and data mesh are not competitors. The lakehouse is an architecture (technology); the data mesh is an operating model (organization and ownership). You can — and MetroPulse does — run a data mesh on top of a lakehouse.

06 / THE FOUNDATIONAmazon S3 — the floor everything else stands on

If you remember one thing for Domain 1, make it S3. It is the gravitational center of data on AWS: the lake, the SageMaker training-data source, the Firehose destination, the model-artifact store. It offers eleven 9's of durability (99.999999999%) by redundantly storing objects across multiple devices and Availability Zones within a Region. Let's wire up the features MetroPulse actually relies on.

Buckets, zones, and partitioning

We organize the lake by zone and partition aggressively by date so query engines can prune. A telemetry object's key looks like:

s3://metropulse-datalake/bronze/telemetry/year=2026/month=06/day=02/hour=14/part-0007.json

That key structure isn't cosmetic — Athena and Spark read the year=/month=/day= prefixes as partition columns and skip everything irrelevant to a query.

Storage classes & lifecycle: paying for data by temperature

Telemetry is scorching hot on day one and frozen by day ninety. Paying S3 Standard rates forever would be wasteful, so we let data flow down the cost curve automatically.

// S3 lifecycle policy for the Bronze zone

{
  "Rules": [{
    "ID": "bronze-telemetry-tiering",
    "Filter": { "Prefix": "bronze/telemetry/" },
    "Status": "Enabled",
    "Transitions": [
      { "Days": 30,  "StorageClass": "STANDARD_IA" },
      { "Days": 90,  "StorageClass": "GLACIER_IR" },
      { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
    ],
    "Expiration": { "Days": 2555 }   // delete after 7 years
  }]
}
Cost gotcha The “Infrequent Access” and Glacier classes have minimum storage durations (30/90/180 days) and per-GB retrieval fees. Transitioning tiny, frequently-read objects into them can cost more than S3 Standard. Tier by temperature, not by reflex.

Versioning & replication: protecting the lake

Versioning keeps every iteration of an object, so an accidental overwrite of a curated training set is recoverable and deletes become reversible (delete markers). It's also a prerequisite for S3 Replication. We enable Cross-Region Replication (CRR) to copy the Gold zone into a second Region for disaster recovery and to put data closer to a remote analytics team — while Same-Region Replication (SRR) can aggregate logs across accounts.

Security: bucket policies, encryption, access points

The lake holds rider PII, so security is layered. First, a bucket policy denies any non-TLS request outright:

{
  "Sid": "DenyInsecureTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::metropulse-datalake/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}

Next, encryption at rest. All new S3 objects are encrypted by default; the question is which key model:

OptionWho manages keysWhen to use
SSE-S3AWS (AES-256), fully managedDefault, zero overhead
SSE-KMSAWS KMS keys you control + auditNeed key rotation, access logs, separation of duties
DSSE-KMSTwo independent layers of KMS encryptionStrict regulatory “dual-layer” mandates
SSE-CYou supply the key per requestYou must hold keys outside AWS

MetroPulse uses SSE-KMS on the lake (auditable via CloudTrail), and applies DSSE-KMS to the Payments domain where dual-layer encryption is contractually required.

Finally, S3 Access Points give each team its own named endpoint and policy onto the shared bucket — the Fleet domain's access point can't even see the Payments prefix. And S3 Object Lambda lets us transform objects on the way out: analysts reading rider records get a view with PII automatically redacted by a Lambda, without ever duplicating the dataset.

Event notifications: the lake that reacts

When Firehose writes a new Bronze object, an S3 Event Notification fires. We route it to EventBridge, which triggers the Glue job that promotes Bronze → Silver. The lake isn't a passive bucket; it's an event-driven pipeline trigger.

Exam lens Expect “pick the cheapest option that meets the SLA” questions. Keywords decide the answer: “unknown/changing access” → Intelligent-Tiering; “single-digit-ms, latency-sensitive ML” → Express One Zone; “milliseconds but rarely accessed” → Glacier Instant Retrieval; “redact PII without copying data” → Object Lambda; “per-team scoped access to one bucket” → Access Points.

07 / COMPUTE STORAGEEBS, EFS & FSx — feeding the training instances

S3 is object storage: brilliant for the lake, but you can't mount it as a normal filesystem for a training job that needs millions of fast random reads. That's where block and file storage come in. This trio is a perennial exam favorite because the distinctions are crisp once you see them side by side.

In MetroPulse, each SageMaker training instance gets EBS volumes for its OS and local scratch space. The data-science team shares feature notebooks and reference datasets over a single EFS mount so nobody re-downloads 200 GB to their own machine. And when we run a large distributed training job that must stream terabytes of Parquet at maximum throughput, we attach FSx for Lustre, which links directly to the S3 lake and presents it as a blisteringly fast POSIX filesystem.

Exam lens Decode by keyword: “single instance, block device, boot volume” → EBS · “shared across many Linux instances” → EFS · “high-performance computing / Lustre / fastest ML training throughput from S3” → FSx for Lustre · “Windows file shares” → FSx for Windows.

08 / REAL-TIME INGESTIONKinesis & Apache Flink — catching data in motion

Now the heart of the velocity problem. MetroPulse can't wait for a nightly batch to discover a scooter's battery is failing — it needs to know in seconds. This is the streaming stack.

Kinesis Data Streams: the durable pipe

Amazon Kinesis Data Streams is a managed, ordered, replayable stream. Its unit of capacity is the shard: each shard ingests up to 1 MB/s (or 1,000 records/s) and reads at 2 MB/s. You scale by adding shards (provisioned mode) or let on-demand mode handle it automatically. Data is retained from 24 hours up to 365 days, so multiple consumers can read — and re-read — the same events independently.

The partition key decides which shard a record lands on. We key by vehicle_id so all of one vehicle's events stay ordered on the same shard:

import boto3, json
kinesis = boto3.client("kinesis")

kinesis.put_record(
    StreamName="metropulse-telemetry",
    Data=json.dumps(event),
    PartitionKey=event["vehicle_id"]   # keeps a vehicle's events ordered
)

Managed Service for Apache Flink: real-time anomaly detection

Reading from the stream is Amazon Managed Service for Apache Flink (formerly Kinesis Data Analytics). It runs continuous computations over the stream. Crucially for an ML platform, its SQL engine ships a built-in RANDOM_CUT_FOREST function — an unsupervised, streaming anomaly-detection algorithm that learns the normal pattern of numeric data and scores each new record by how distant it is from the rest. No labels, no separate model to deploy — anomaly detection right inside the pipeline.

// Streaming anomaly detection in Flink SQL

CREATE OR REPLACE STREAM "ANOMALY_STREAM" (
    vehicle_id     VARCHAR(16),
    battery_drain  DOUBLE,
    trip_distance  DOUBLE,
    anomaly_score  DOUBLE
);

CREATE OR REPLACE PUMP "ANOMALY_PUMP" AS
INSERT INTO "ANOMALY_STREAM"
SELECT STREAM vehicle_id, battery_drain, trip_distance, anomaly_score
FROM TABLE(
    RANDOM_CUT_FOREST(
        CURSOR(SELECT STREAM vehicle_id, battery_drain, trip_distance
                FROM "SOURCE_SQL_STREAM_001")
    )
);  -- high anomaly_score → batteries failing / possible fraud

Amazon Data Firehose: the no-code delivery hose

While Flink watches for anomalies, every event must also be archived to the lake. That's Amazon Data Firehose (formerly Kinesis Data Firehose) — a fully managed, near-real-time delivery service that buffers records (by size or time), can transform them with Lambda, convert JSON to Parquet on the fly, and lands them in S3 (or Redshift, OpenSearch, etc.). It's serverless with no shards to manage; you trade a little latency (the buffer window) for zero operational overhead.

Tuning & troubleshooting

The classic Kinesis failure mode is ProvisionedThroughputExceededException — a “hot shard.” Usually the culprit is a poorly distributed partition key sending too much traffic to one shard. Fixes: choose a higher-cardinality key, reshard (split the hot shard), switch to on-demand mode, or use the Kinesis Producer Library (KPL) to batch and aggregate records. For consumers that compete for the 2 MB/s read limit, enhanced fan-out gives each consumer its own dedicated 2 MB/s pipe via a push model.

09 / KAFKA ON AWSAmazon MSK — when the org speaks Kafka

MetroPulse's partner transit agencies already run Apache Kafka. Rebuilding their producers for the Kinesis API would be wasteful, so for that ingestion path we use Amazon MSK (Managed Streaming for Apache Kafka) — fully managed, open-source-compatible Kafka. Producers keep speaking the Kafka protocol; AWS runs the brokers, patching, and Zookeeper/KRaft plumbing.

Two companions matter: MSK Connect is managed Kafka Connect, so we stream topics into S3 or a database with configuration instead of custom consumer code. MSK Serverless removes broker sizing entirely — it auto-provisions and scales capacity and manages partitions for you, much like Kinesis on-demand.

Kinesis Data Streams vs Amazon MSK

DimensionKinesis Data StreamsAmazon MSK
ProtocolKinesis API (AWS SDK)Apache Kafka protocol
Unit of scaleShard (1 MB/s in · 2 MB/s out)Broker + partition count
Auto-scalingOn-demand modeMSK Serverless
Ops overheadLowest — fully serverlessHigher (provisioned); low (Serverless)
EcosystemDeep native AWS integrationHuge open-source Kafka ecosystem
Best when…Greenfield, AWS-native, simplicityExisting Kafka, portability, Connect connectors
Exam lens The deciding word is almost always present. “Existing Kafka / open-source / migrate / Kafka Connect” → MSK. “Serverless / simplest / tight AWS integration / no infrastructure” → Kinesis Data Streams. If they mention “Kafka without managing brokers” → MSK Serverless.

10 / GLUE & FLOWETL pipelines & orchestration

Raw Bronze data isn't model-ready — it has duplicates, GPS drift, and the wrong format. ETL (Extract, Transform, Load) is the cleaning and reshaping stage. AWS Glue is the serverless workhorse: it crawls our S3 data to populate the Glue Data Catalog (the metadata layer that makes the lake queryable), and runs Spark jobs to dedupe, validate, and rewrite JSON to partitioned Parquet — moving data Bronze → Silver → Gold.

One detail worth flagging for ML: the distinction between ETL (transform before loading — good for structured warehouse targets) and ELT (load raw, transform later — natural for the lakehouse, where cheap storage lets you keep everything and transform on demand). MetroPulse leans ELT into Bronze, then ETL forward.

None of this runs by hand. Orchestration sequences the steps, handles retries, and enforces dependencies. We use AWS Step Functions for event-driven, serverless workflows (S3 event → validate → Glue job → quality check → publish), and Amazon MWAA (managed Apache Airflow) when teams already author DAGs in Python. EventBridge handles scheduled and event triggers.

11 / ZOOM OUTThe complete picture

Every box in Fig 1 now has a reason to exist. Trace one telemetry event end to end:

  1. A scooter emits a JSON heartbeat → Kinesis Data Streams (partitioned by vehicle_id).
  2. Managed Service for Apache Flink scores it with RANDOM_CUT_FOREST; a high score fires a real-time alert to dispatch.
  3. In parallel, Amazon Data Firehose buffers, converts to Parquet, and lands it in the S3 Bronze zone.
  4. The S3 write fires an event notification → EventBridge → Step Functions → AWS Glue cleans and promotes Bronze → Silver → Gold.
  5. Lifecycle rules age aging data down through the storage classes; SSE-KMS encrypts it; CRR replicates Gold for DR.
  6. SageMaker training jobs read curated Parquet — over FSx for Lustre for throughput, with EBS scratch and a shared EFS mount for the team.

That's a complete, defensible data ingestion and storage layer — and it's exactly the kind of reasoning the MLA-C01 rewards: not “what does service X do,” but “which service, and why, for this requirement.”

12 / REVISIONPart 1 cheat-sheet: ingestion & storage

Lock these in before exam day

  • S3 is the center of gravity. Lake, training source, Firehose target, model store. Know storage classes, lifecycle, versioning, replication, encryption (SSE-S3 / SSE-KMS / DSSE-KMS / SSE-C), Access Points, Object Lambda, and event notifications cold.
  • Storage class = data temperature + access SLA. Unknown pattern → Intelligent-Tiering. Latency-critical ML → Express One Zone. Cheap-but-instant → Glacier Instant Retrieval. Deep archive → Glacier Deep Archive.
  • Block vs file vs object. EBS = single-instance block. EFS = shared multi-instance Linux file. FSx for Lustre = high-throughput HPC/ML, links to S3. S3 = object lake.
  • Streaming trio. Kinesis Data Streams = durable, replayable, sharded pipe. Managed Service for Apache Flink = real-time compute (RANDOM_CUT_FOREST for anomaly detection). Amazon Data Firehose = no-code buffered delivery to S3/Redshift/etc.
  • Kinesis vs MSK. Greenfield + AWS-native + serverless → Kinesis. Existing/open-source Kafka + Connect ecosystem → MSK (Serverless removes broker management).
  • Mind the renames. Kinesis Data Analytics → Managed Service for Apache Flink. Kinesis Data Firehose → Amazon Data Firehose. Old names still appear in exam-adjacent material.
  • Lakehouse = architecture; data mesh = operating model. They stack, not compete.
  • Formats: row (JSON/Avro) for writes & streaming; columnar (Parquet/ORC) for analytics & ML reads.

That's the ingestion-and-storage half of Domain 1. The data is now landing, durable, secured, and organized — but it's still raw. Part 2 picks up exactly here: cleaning and validating that data, engineering features, handling missing values and class imbalance, and detecting bias and PII before any model ever sees it.
